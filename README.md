# АИС «Умный обходчик»

Решение кейса РМК Digital на хакатоне «ИТы-Герой», апрель 2026.
Команда «Ракета» - **2 место в кейсе РМК, 6 место из 15 команд финала** (163 балла, у первого места 173).

Прототип собран за 24 часа.

---

## Задача

Обходчик энергоцеха за смену проверяет десятки приборов. Показания записываются на бумагу и попадают в учётную систему только к следующему дню - плюс ошибки ручного ввода и нечитаемый почерк.

Нужно сократить путь от снятия показания до его появления у мастера смены.

## Решение

Веб-приложение, которое открывается на телефоне по ссылке, без установки из стора.

1. Обходчик открывает карточку прибора и фотографирует шкалу
2. Фото уходит на сервер, показание распознаётся через Yandex Vision OCR
3. Сервер сам сверяет значение с нормой прибора и помечает выход за границы
4. Мастер смены видит результат на своём дашборде в течение нескольких секунд

## Стек

| Слой | Технологии |
|---|---|
| Backend | Django 5, Django REST Framework |
| База данных | PostgreSQL 16 |
| Распознавание | Yandex Vision OCR API |
| Frontend | Vanilla JS, Tailwind (CDN), SPA в одном файле |
| Инфраструктура | Docker, docker-compose, деплой в Amvera |

## Запуск

```bash
git clone https://github.com/ecl1pse192/rmk-smart-walker-hackathon
cd rmk-smart-walker-hackathon
cp .env.example .env   # файл нужно создать, см. ниже
docker compose up
```

В `docker-compose.yml` указан `env_file: .env`, поэтому **без этого файла запуск упадёт**. Минимальное содержимое:

```
YANDEX_API_KEY=<ключ сервисного аккаунта>
YANDEX_FOLDER_ID=<идентификатор каталога>
```

Приложение поднимется на `http://localhost:8000`, миграции применяются автоматически при старте контейнера. Без ключей Yandex приложение запустится, но создание показания вернёт ошибку валидации.

## Архитектура

```
Телефон (SPA)
     |
     |  POST фото (multipart)
     v
Django + DRF  ---- base64 ---->  Yandex Vision OCR
     |                                  |
     |  <------ распознанный текст -----+
     |
     |  regex -> Decimal
     |  сверка с normal_min / normal_max
     v
PostgreSQL
     |
     v
Дашборд мастера (поллинг раз в 3 сек)
```

### Модели

- `Worker` - сотрудник (табельный номер, ФИО, роль)
- `Equipment` - прибор, цех, границы нормы (`normal_min` / `normal_max`)
- `Route` - маршрут обхода, M2M с оборудованием
- `Inspection` - конкретный обход
- `Reading` - показание: фото, распознанное значение, флаг выхода за норму
- `Defect` - дефект: описание, критичность, фото

Все первичные ключи - UUID.

### API

Роутер DRF с префиксом `/api/`:

| Endpoint | Назначение |
|---|---|
| `/api/equipment/` | Список оборудования с границами нормы |
| `/api/readings/` | Создание показания (запускает OCR), чтение для дашборда |
| `/api/defects/` | Регистрация дефекта |
| `/api/workers/`, `/api/routes/`, `/api/inspections/` | CRUD, во фронте не задействованы |

### Решение, которое стоит отметить

`value` и `is_out_of_norm` объявлены `read_only` в сериализаторе и вычисляются **на сервере**. Клиент отправляет только фотографию, оборудование и обход - подделать показание с устройства нельзя. Для промышленного учёта это принципиально: данные должны быть неоспоримы.

## Ограничения MVP

Раздел написан честно - это прототип за 24 часа, а не продукт.

**Офлайн не реализован.** `sw.js` содержит только `skipWaiting()` и `clients.claim()` - без `fetch`-листенера и без `Cache Storage`. Приложение устанавливается на домашний экран как PWA, но без сети не откроется. IndexedDB не используется.

В `localStorage` (ключ `inspectionStateV1`) хранится состояние текущего обхода: таймер, снятые показания, зарегистрированные дефекты. При обновлении страницы обход продолжается. Но очереди отложенной отправки нет - если сеть пропала, запрос упадёт в `catch`, и автоматически он не повторится.

**Нет аутентификации.** Вход по PIN не реализован, permissions в DRF - `AllowAny`, `CORS_ALLOW_ALL_ORIGINS = True`. Для демо приемлемо, для эксплуатации - нет.

**OCR берёт первое число из всего распознанного текста.** Regex `(\d+(?:[.,]\d+)?)` не различает показание, дату на корпусе и цифры шкалы. Логики зон интереса нет.

**Маршруты и обходы не подключены к интерфейсу.** Модели `Route` и `Inspection` существуют и торчат в API, но SPA их не использует - `inspection_id` захардкожен константой. Если такого обхода нет в базе, запросы упадут по внешнему ключу.

**Карта цеха - декоративная.** У `Equipment` нет полей координат, пины раскладываются автосеткой поверх статичного SVG.

**Нет тестов, нет CI/CD.** Деплой выполнялся вручную через панель Amvera.

**Конфигурация небезопасна для эксплуатации.** Это стоит назвать отдельно, потому что проект был развёрнут в облаке:

- в `Dockerfile` при каждом старте создаётся суперпользователь `admin` с паролем, захардкоженным прямо в команде запуска
- `DJANGO_SECRET_KEY` лежит в `docker-compose.yml` открытым текстом
- `DJANGO_DEBUG=1`
- приложение запускается через `manage.py runserver` - это отладочный сервер Django, для эксплуатации нужен WSGI-сервер вроде gunicorn
- порт PostgreSQL проброшен на хост
